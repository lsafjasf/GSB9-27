# 一致性哈希环（虚拟节点 + 加权）

纯 Python 3 标准库实现，解决缓存节点上下线时取模分配导致的大面积键失效问题。

## 文件

- `consistent_hash.py` — 库：`HashRing(vnodes=160)`，`add_node/remove_node/get_node/map_keys`
- `test_consistent_hash.py` — 单元测试与边界用例（11 个）
- `benchmark.py` — 迁移比例、分布偏差曲线、百万键性能实测

## 运行命令

```bash
python3 -m unittest test_consistent_hash -v   # 自测
python3 benchmark.py                          # 实测数据
```

## 设计

- 每个节点按 `vnodes × weight` 个虚拟节点上环，哈希输入为 `节点名#序号`（MD5 取前 64 位），
  跨进程确定；环是排序后的 `(point, node)` 列表，查询用 `bisect` 二分，O(log 环规模)。
- 键的归属只由环决定：排序键包含节点名，与注册顺序无关（有测试保证）。
- 权重为零的节点不上环、不接收任何键；环为空时 `get_node` 抛 `RuntimeError`。

## 实测数据（Python 3.12，x86-64）

### 迁移比例 vs 理论下限（10 节点，20 万键，vnodes=160）

| 操作 | 实际迁移 | 理论下限 | 无关迁移 |
|---|---|---|---|
| 增 1 节点 | 7.82%（=新节点实际份额） | 1/11 ≈ 9.09% | 0 |
| 删 1 节点 | 10.16% | 1/10 = 10.00% | 0 |

- 理论下限 = 变化节点应承担的公平份额；实测围绕下限波动（虚拟节点是随机采样，
  新节点份额 7.82% 略低于 9.09% 属正常涨落，增大 vnodes 可收敛）。
- **无关迁移恒为 0**：增节点时只有迁往新节点的键移动，删节点时只有原属该节点的键移动，
  由一致性哈希的顺时针接管性质保证，并有测试断言。

### 虚拟节点数 vs 分布偏差（10 等权节点，10 万键）

| vnodes/节点 | 最大偏差 | 标准差/均值 |
|---|---|---|
| 10 | 62.2% | 27.0% |
| 25 | 30.6% | 16.2% |
| 50 | 15.1% | 8.2% |
| 100 | 9.9% | 5.5% |
| 160 | 12.9% | 5.1% |
| 200 | 7.8% | 4.7% |
| 400 | 9.5% | 5.3% |
| 800 | 5.2% | 3.1% |
| 1600 | 4.6% | 3.3% |

偏差大致按 1/√vnodes 收敛（单次运行有噪声）。

### 性能（100 万次查询，10 节点 × 160 虚拟节点 = 1600 点环）

- 总耗时 0.54s，单次约 0.54µs，约 1.8M QPS。

## 默认 vnodes=160 的依据

- 100~200 区间偏差已进入个位数百分比（CV ≈ 5%），继续增大收益递减；
- 环规模 = vnodes × Σweight，160 时千级节点也只有十几万点，重建与内存开销可忽略，
  查询为 O(log) 二分，实测百万键亚微秒级；
- 与 memcached 客户端生态的常见取值（ketama 每节点 100~160 点）一致。

## 边界用例覆盖（test_consistent_hash.py）

- 单节点：全部键归该节点；删到剩一个节点亦然。
- 节点全部下线：环为空，`get_node` 抛 `RuntimeError`。
- 权重为零：不占环、不接收键，其他节点增删后仍不接收。
- 键数远大于环规模：20 万键 vs 12 点环，映射完整且确定。
- 另含：注册顺序无关、权重比例（3:1 实测份额比）、重复注册/删未知节点报错。
